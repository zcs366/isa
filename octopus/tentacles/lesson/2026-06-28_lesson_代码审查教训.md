# 代码审查教训 — 审验者之耻

**关键词**：代码审查, 测试通过≠代码正确, 读代码, 八触须, 踩坑, 军师失职

## 起因

2026-06-28，子贡完成8个任务（统一检索/insight/status/插件集成/无损压缩/子Agent隔离/输出验证/行为反馈），测试98/98全过。军师只跑了测试就说"验收通过"，**没有读一行代码**。

用户逼问："看代码了没有？难道没有改进或修改的建议？"

军师被迫逐文件审查，发现**6个致命bug + 7个严重问题**。

## 根因分析

**军师的审验方法错了。**

```
军师的做法：跑测试 → 98/98全过 → "验收通过"
正确的做法：读代码 → 发现问题 → 跑测试验证修复 → "验收通过"
```

**测试通过 ≠ 代码正确。** 测试只验证了"设计者想测试的路径"，没有验证"代码实际走的路径"。

具体根因：
1. **信任过度**：子贡之前的交付质量高，形成了"测试过了就没事"的路径依赖
2. **懒惰**：读422行代码比跑一行测试费力，选择了省力的方式
3. **审验标准缺失**：没有一个"代码审查清单"强制要求逐行读代码

## 铁律（永不再犯）

### 审验铁律

1. **先读代码再跑测试。** 代码审查 > 测试通过。读代码发现的问题是根本性的，测试发现的问题是表面的。
2. **逐函数读，不跳行。** 每个函数的每一行都要过眼。"看起来没问题"不等于"没问题"。
3. **检查边界条件。** 空输入、重复输入、超长输入、多词查询——这些是bug的温床。
4. **检查命名一致性。** `session.db` vs `sessions.db`、`turns` vs `messages`——命名不一致是代码审查的第一信号。
5. **检查硬编码。** `128000`、`role == "user" or role == "user"`——硬编码是偷懒的标志。

### 交付铁律

1. **测试通过是最低门槛，不是最高标准。** 测试过了只是"能跑"，不是"正确"。
2. **子贡交付 ≠ 军师审验通过。** 军师必须独立审验，不能委托信任。
3. **用户逼问 = 军师失职。** 如果用户需要逼问"你读代码了吗"，说明军师的审验流程有根本缺陷。

## 教训一句话

**跑测试是验收的最后一步，不是第一步。第一步永远是读代码。**
