# 代码审查铁律 — 审验标准备忘录

**关键词**：代码审查, 审验铁律, 测试通过, 读代码, 先读后测, 八触须

## 核心教训

**测试通过 ≠ 代码正确。** 2026-06-28，子贡8任务98/98测试全过，军师只跑测试不读代码就说验收通过。用户逼问后逐文件审查发现**6致命+7严重bug**。

## 审验铁律（5条）

1. **先读代码再跑测试。** 代码审查 > 测试通过。
2. **逐函数读，不跳行。** 每个函数每一行过眼。"看起来没问题"≠"没问题"。
3. **检查边界条件。** 空输入/重复输入/超长输入/多词查询=bug温床。
4. **检查命名一致性。** `session.db` vs `sessions.db`、`turns` vs `messages`=第一信号。
5. **检查硬编码。** `128000`、`role == "user" or role == "user"`=偷懒标志。

## 交付铁律（3条）

1. **测试通过是最低门槛，不是最高标准。** 测试过了="能跑"，不是"正确"。
2. **子贡交付 ≠ 军师审验通过。** 军师必须独立审验，不能委托信任。
3. **用户逼问 = 军师失职。** 用户需要逼问"你读代码了吗"=审验流程有根本缺陷。

## 典型致命bug

| bug | 文件 | 为什么测试没发现 |
|-----|------|-----------------|
| 整串匹配 | unified_search.py | 测试用单词查询，没测多词 |
| db名少s | context_mapper.py | 测试mock了路径，没测真实db |
| 死重检测永远=1 | context_mapper.py | 测试没验证死重数量 |
| 铁律文字误导 | plugins/jika/__init__.py | 测试只检查"含🔴标记"，没检查文字内容 |

## 检查清单（审验时逐项过）

```
□ 每个函数的每一行代码是否读过？
□ 字符串匹配是整串还是分词？
□ 文件名/路径是否与实际一致？
□ 硬编码数字是否应参数化？
□ 条件判断是否有重复/遗漏？
□ 去重/防重逻辑是否存在？
□ O(n²)循环是否存在？
□ 注入的文字是否准确/不误导？
□ 降级方案是否存在？
□ 测试是否覆盖了边界条件？
```
