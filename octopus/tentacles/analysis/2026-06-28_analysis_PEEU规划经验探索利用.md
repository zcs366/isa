## 二、核心方法

### 2.1 问题背景

GUI Agent（图形用户界面智能体）的核心挑战在于**任务规划**——将复杂任务分解为可执行动作。小规模开源多模态大语言模型（MLLM）虽然成本低、隐私保护强，但存在两个致命弱点：
1. **规划能力弱（Weak Planning）**：无法有效分解跨步骤、多条件约束的复杂任务
2. **跨网站泛化差（Limited Cross-Website Generalization）**：训练过的网站表现尚可，未见过的网站大幅退化

### 2.2 两个已有范式及其局限

| 范式 | 方法 | 局限 |
|------|------|------|
| **原子级任务训练（Atomic-level）** | 比较操作前后环境状态变化，提取"点击/输入/滚动"等原子经验，合成为训练数据 | 不清楚原子技能能否泛化到高层规划任务 |
| **粗糙高层任务训练（Coarse high-level）** | 直接用探索轨迹中的原始任务描述作为训练任务 | 轨迹与任务存在**不对齐**问题（如任务要求4.5星但轨迹只展示了4星的动作），缺乏严格约束 |

### 2.3 PEEU方法（三步法）

PEEU（Planning Experience Exploration and Utilization）整体分为**两大阶段**展开，实质包含**三个关键步骤**：

```
┌─────────────────────────────────────────────────────────┐
│  Stage 1: 自主探索                                       │
│  ┌──────────────┐    ┌──────────────────────────────┐    │
│  │ 自驱动任务生成 │ →  │ 自治探索 → 探索树 ℛ = (V,E) │    │
│  │ 𝒟 = M(s₀,URL) │    │ τ = {(s₀,a₀),...,(sₘ,aₘ)} │    │
│  └──────────────┘    └──────────────────────────────┘    │
├─────────────────────────────────────────────────────────┤
│  Stage 2: Hindsight经验利用                               │
│  ┌────────────────┐  ┌──────────────────┐  ┌──────────┐ │
│  │ ① 原子经验提取  │→│② 轨迹级经验聚合  │→│③ 任务精炼 │ │
│  │ εₜ=M(sₜ,aₜ,   │  │ μ=(ε₁,ε₂,...,ε_T)│  │ 𝒟̃=Φ(μ,M) │ │
│  │     sₜ₊₁)      │  │                  │  │          │ │
│  └────────────────┘  └──────────────────┘  └──────────┘ │
├─────────────────────────────────────────────────────────┤
│  训练: π: 𝒮 × ℋ × 𝒟̃ → 𝒜  via SFT + GRPO                │
└─────────────────────────────────────────────────────────┘
```

#### 步骤一：规划树探索（Planning Tree Exploration）

**核心思想**：让Agent像人一样，**自主设定学习目标**，然后主动探索环境。

1. **自驱动任务生成**：给定网站URL和首页状态 `s₀`，探索Agent自动生成任务列表：
   ```
   𝒟 = M(s₀, URL)
   ```
   例如面对电商网站，Agent可能生成"搜索商品"、"添加到购物车"、"结算"等任务。

2. **自治探索执行**：Agent基于任务列表和完整环境信息，执行自主探索，生成**有向探索树**：
   ```
   ℛ = Explore(M, 𝒟, Env, URL)
   ```
   探索树 `ℛ = (V, E)` 中：
   - **V** = 网页截图状态（所有轨迹共享首页根节点 `s₀`）
   - **E** = 动作边（点击、输入、滚动等）
   - 每条轨迹 `τ = {(s₀, a₀), ..., (sₘ, aₘ)}` 是一条完整的交互路径

**关键优势**：与被动使用预定义数据集不同，PEEU的探索是**自适应的**——任务由Agent自己根据网站功能特点生成，而不是人工标注，因而更贴合网站的实际功能结构。

#### 步骤二：Hindsight经验提取与聚合（Planning Experience Utilization）

> 这是PEEU最核心的创新——**利用后见之明（Hindsight）视角**，从事后角度审视完整轨迹，提取真正有价值的经验，然后用这些经验来**修正和高精化原始任务描述**。

**原子经验提取**：MLLM对比**动作前状态** `sₜ` 和**动作后状态** `sₜ₊₁`：
```
εₜ = M(sₜ, aₜ, sₜ₊₁)
```
每一个原子经验 `εₜ` 描述的是"在这个状态下执行这个动作会导致什么状态变化"——本质上是**因果知识**。

**轨迹级经验**：将一条轨迹上的所有原子经验串联：
```
μ = (ε₁, ε₂, ..., ε_T)
```

**任务精炼（最关键一步）**：Agent将所有轨迹级经验聚合，自动生成**精炼后的高级任务**：
```
𝒟̃ = (d̃₁, d̃₂, ..., d̃ₙ) = Φ(μ₁, μ₂, ..., μₙ, M)
```
这里的 `Φ` 不是简单的串联或过滤，而是**融合（fuse）**——把原子经验中蕴含的因果关系、约束条件、步骤顺序等信息，改写成**与轨迹严格对齐且约束明确的高层任务描述**。

**精炼后的任务 `𝒟̃` 相比于原始任务 `𝒟` 的三个提升**：
1. **对齐（Aligned）**：任务描述精确匹配轨迹中实际发生的事情
2. **严格约束（Strictly Constrained）**：包含了轨迹中实际执行的条件（如"4星及以上商品"而非模糊的"找商品"）
3. **高层抽象（High-level）**：保持了任务的高层语义而非退化为原子操作列表

#### 步骤三：策略学习

精炼后的任务-轨迹对用于训练规划策略 `π`：
```
π: 𝒮 × ℋ × 𝒟̃ → 𝒜
```
其中 `𝒮` = 当前状态，`ℋ` = 历史状态，`𝒟̃` = 精炼任务描述，`𝒜` = 动作空间。

训练使用两种范式：
- **SFT（Supervised Fine-Tuning）**：监督微调，适用于大规模数据（2k轨迹）
- **GRPO（Group Relative Policy Optimization）**：强化学习，适用于小规模数据（0.1k轨迹）

### 2.4 TDHAF分析框架

TDHAF（Task Decomposition Hierarchical Analysis Framework）是论文提出的**诊断工具**，用于系统性分析不同粒度任务训练的泛化能力。

#### 三级任务粒度

| 粒度 | 定义 | 示例 |
|------|------|------|
| **Low-level（低层）** | 单步原子操作 | "点击搜索按钮"、"在输入框键入'Python'" |
| **Mid-level（中层）** | 多步子任务 | "填写搜索表单并提交"（包含点击输入框 + 键入 + 点击搜索） |
| **High-level（高层）** | 长视野复合任务 | "购买一台价格低于5000元、评价4星以上的笔记本电脑" |

#### 三维泛化分析

| 维度 | 问题 | 意义 |
|------|------|------|
| **ID Bottom-up（域内自底向上）** | 低层技能训练能否泛化到高层任务？ | 检验原子技能→规划能力的迁移 |
| **ID Top-down（域内自顶向下）** | 高层训练能否覆盖低层技能？ | 检验高层规划是否包含子技能 |
| **OOD Multi-level（跨域多层）** | 哪个粒度的任务训练在未见网站上泛化最好？ | 指导训练策略选择 |

## 三、关键结果

### 3.1 主实验结果（Table 1）

#### 7B模型, 2k轨迹

| 方法 | 总体准确率 | 超越基线 |
|------|-----------|---------|
| Vanilla（基线未训练） | 7.8% | — |
| Coarse-SFT | 19.0% | +11.2% |
| Atomic-SFT | 21.7% | +13.9% |
| **PEEU-SFT（Our）** | **30.6%** | **+22.8%** |
| *Qwen2.5-VL-32B（对比）* | *22.7%* | — |
| *Qwen2.5-VL-72B（对比）* | *29.3%* | — |

**结论：PEEU的7B模型（30.6%）不仅大幅超过32B模型（22.7%），甚至超过了72B模型（29.3%）——这是"以小博大"的重要证据。**

#### 7B模型, 0.1k轨迹（小数据场景）

| 方法 | 总体准确率 |
|------|-----------|
| Vanilla | 7.8% |
| Atomic-GRPO | 10.0% |
| Coarse-GRPO | 11.5% |
| **PEEU-GRPO（Ours）** | **19.9%** |

#### 3B模型, 0.1k轨迹（极轻量级场景）

| 方法 | 总体准确率 |
|------|-----------|
| Vanilla | 0.2% |
| Coarse-GRPO | 5.6% |
| Atomic-GRPO | 5.5% |
| **PEEU-GRPO（Ours）** | **11.1%** |

### 3.2 三大关键发现

#### 发现一：适配任务使其匹配轨迹（Adapt Task to Fit Trajectory with Experience）

> 传统"Coarse"（粗糙）方法的问题是**任务与轨迹不对齐**。例如：
> - 原始任务：*"在Amazon上找到一台评分4.5星以上的雪板"*
> - 实际轨迹：*Agent浏览了评分4星的雪板页面，没有看到4.5星以上的*
> - **问题**：任务要求与轨迹内容矛盾，训练信号混乱
> - **PEEU方案**：利用hindsight经验修正任务 → *"在Amazon上查看雪板信息"* → 与轨迹严格对齐

PEEU-SFT（7B, 2k）达到**30.6%**，超过Qwen2.5-VL-32B（22.7%）和Qwen2.5-VL-72B（29.3%），证明了**经验驱动的任务修正远比扩大模型规模更有效**。

#### 发现二：低层原子技能 ≠ 高层规划能力（反直觉核心发现）

> **这是论文最反直觉的发现**，也是对整个"GUI Agent训练范式"发出警告的关键论据。

**TDHAF Bottom-up测试结果**：

| 模型 | 低层任务准确率 | 高层任务准确率 | 差距 |
|------|--------------|--------------|------|
| 3B模型 | **80.5%** | **9.1%** | -71.4% |
| 7B模型 | **89.6%** | **18.8%** | -70.8% |

**含义**：模型可以把原子操作学得极好（80-90%），但在需要把这些原子操作**编排成完整规划**时，性能断崖式下跌至个位数（9-18%）。**原子技能的高分是假象**——它掩盖了规划能力的严重缺失。

**这正是PEEU的价值所在**：
- Atomic-SFT（原子级训练）：21.7%
- PEEU-SFT（高层训练）：30.6%
- **差距：+8.9%，且PEEU的训练数据正是从原子经验聚合而来**

#### 发现三：高层任务训练产生更强的OOD泛化

| 泛化类型 | 最佳训练粒度 | 证据 |
|---------|-------------|------|
| ID Bottom-up | 高层训练（High-level） | 高层训练对低层也有75-85%覆盖率 |
| ID Top-down | 高层训练（High-level） | 高层训练正向泛化优于低层逆向泛化 |
| **OOD Multi-level** | **高层训练（High-level）** | PEEU-SFT 30.6%远超Atomic-SFT 21.7% |

### 3.3 Prompt vs 训练对比

| 方法类型 | 7B结果 | 3B结果 |
|---------|--------|--------|
| Atomic-Prompt（检索式） | 3.7% | 0.0% |
| Trajectory-Prompt（检索式） | 3.7% | 0.0% |
| PEEU-GRPO（训练式） | **19.9%** | **11.1%** |

**结论："对小模型来说，直接训练远优于检索增强。"** 即使只检索10条最相关的原子经验作为上下文，小模型也无法有效利用——它们需要的是**内置的策略知识**而非弹性的上下文记忆。

## 四、与Hermes Agent的关联

### 4.1 对子贡/子产/萧何/鲁班编排的警示

PEEU的反直觉发现对Hermes的多智能体编排体系有深刻的警示意义：

| 编排组件 | 原子技能焦点 | 规划能力风险 | PEEU警示 |
|---------|-------------|-------------|----------|
| **子贡（贸易/调度）** | 多工具调用、API编排 | 多步骤约束满足 | 子贡可能在单个API调用上做到近乎完美，但在**将多个带约束的API编排成完整工作流**时失败。任务描述与执行轨迹的**对齐**是关键 |
| **子产（执行）** | 高精度原子执行 | 自主探索能力 | 子产的原子执行越强，越容易掩盖其**自适应规划**的缺失。PEEU启示：需要让子产在**未见过的工作流**上进行自主探索式训练 |
| **萧何（记忆/检索）** | 知识检索、经验注入 | 经验→规划的转化 | Atomic-Prompt的惨败（3.7%）说明：**仅仅检索经验注入context是不够的**。萧何需要从"记忆检索器"进化为"经验整合器"——将检索到的经验**融合进模型的决策权重**而非只当上下文 |
| **鲁班（工具制造）** | 工具创建、代码生成 | 长任务分解 | TDHAF的Bottom-up发现直接针对鲁班：能写出正确的工具函数（低层）不等于能设计出正确的工具编排方案（高层）。鲁班需要**规划层（L13）** 的明确介入 |

### 4.2 可迁移方法论

PEEU有四个方法论可直接迁移到Hermes Agent体系：

1. **Hindsight任务精炼（Hindsight Task Refinement）**
   - 概念：执行完毕后再回头看，用实际轨迹修正任务描述
   - 迁移：对子产完成的任务，萧何应做"事后审计"——对比原始任务描述和实际执行轨迹，自动生成更精确的任务规范存入记忆

2. **自主探索树（Self-driven Exploration Tree）**
   - 概念：Agent自己生成探索任务，构建有向探索树
   - 迁移：Hermes的规划层（L13）不应只依赖预定义benchmark，而应让Agent**自己发现网站/环境的边界**，生成探索任务库

3. **原子经验聚合（Atomic Experience Fusion）**
   - 概念：不直接使用原子经验，而是通过LLM将它们**融合**为高层任务
   - 迁移：Hermes的"经验增强"策略应支持多级聚合：原子操作经验 → 步骤级经验 → 任务级经验，形成**经验层级**

4. **训练优先于检索（Train over Retrieve）**
   - 概念：对小模型，将经验训练进权重比作为prompt注入更有效
   - 迁移：Hermes的微调管道应优先考虑用已有经验对Agent进行**增量训练**，而非仅靠注入更多上下文

### 4.3 与17层设计要求L13（规划层）的对位

PEEU直接命中17层设计要求中的**L13（规划层）**，以下是精确对位分析：

| L13设计要求条目 | PEEU对位 | 对位强度 |
|----------------|---------|---------|
| **L13.1: 任务分解能力** | PEEU的核心能力——将复合任务分解为可执行步骤。TDHAF专门分析不同粒度任务的分解与泛化 | P0命中 |
| **L13.2: 约束条件感知** | PEEU的"严格约束"正是从hindsight经验中提取——修正后的任务包含精确的条件要求 | P0命中 |
| **L13.3: 跨域泛化** | PEEU的主要贡献——通过hindsight任务精炼显著提升OOD泛化能力（7B > 32B） | P0命中 |
| **L13.4: 经验驱动的规划改进** | PEEU的完整流程：探索→经验提取→任务精炼→再训练，是**闭环的经验-规划-再训练循环** | P0命中 |
| **L13.5: 规划与执行的对齐** | PEEU解决的核心问题：原始任务描述与轨迹不对齐。精炼后的任务与轨迹严格对齐 | P0命中 |

> **总评**：PEEU是L13（规划层）的**范式级论文**。它揭示了当前GUI Agent领域一个系统性盲区——**原子技能不等于规划能力**——并提供了一个完整的解决方案流水线。这不仅是一个技术贡献，更是对整个领域的**方法学纠偏**。

## 五、结论与待办

### 5.1 论文核心贡献总结

1. **提出了PEEU方法**：一种通过自主探索和hindsight经验利用来训练GUI Agent规划能力的完整流水线，包含规划树探索→经验提取与融合→任务精炼→策略学习的闭环
2. **提出了TDHAF分析框架**：系统性地分析了不同粒度任务训练的泛化特性，揭示"低层原子技能≠高层规划能力"的反直觉规律
3. **实现了7B超32B的突破**：PEEU-SFT（7B, 30.6%）超越Qwen2.5-VL-32B（22.7%）和72B（29.3%），证明了方法本身的价值比模型规模更重要

### 5.2 局限性

1. **依赖于大模型做探索生成**：PEEU的探索阶段使用GPT-4o生成任务和总结经验，整体流程依赖强模型蒸馏
2. **未开源代码和数据**：无法复现实验
3. **仅验证了WebVoyager一个benchmark**：泛化到移动端GUI、桌面GUI的效果未知
4. **0.1k数据场景使用GRPO**：需要确认GRPO效果提升是来自RL还是探索数据的质量
