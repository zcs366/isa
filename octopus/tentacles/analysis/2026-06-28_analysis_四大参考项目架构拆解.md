# 四大参考项目架构拆解

## 绪论

研究四个开源/闭源Agent项目的架构，为openLLM的"硬件化"提供参考。

每个项目回答一个核心问题：
- OpenCode/Claude Code → "Agent怎么循环执行？"
- OpenClaw → "Agent怎么跨平台运行？"
- OpenHuman → "Agent怎么记住用户？"

---

## 一、OpenCode（Go · 已归档→更名Crush）

### 架构

```
OpenCode (Go · 137个.go文件)
├── agent/agent.go        ← Agent循环（758行·核心）
├── permission/           ← 权限系统（119行）
├── session/              ← 会话管理（156行·SQLite）
├── tools/                ← 工具集（bash/edit/write/glob/grep/ls/patch/view）
├── llm/provider/         ← 多模型适配（Anthropic/OpenAI/Gemini/Copilot/Azure）
├── llm/prompt/           ← Prompt模板
├── db/                   ← SQLite存储
├── lsp/                  ← 语言服务器协议
├── tui/                  ← 终端UI（BubbleTea）
└── pubsub/               ← 事件总线
```

### Agent循环（核心）

```go
// agent.go 核心循环（简化）
for {
    // 1. 流式调用LLM
    eventChan := provider.StreamResponse(ctx, msgHistory, tools)
    
    // 2. 处理流式事件（thinking/content/tool_use）
    for event := range eventChan {
        processEvent(ctx, sessionID, &assistantMsg, event)
    }
    
    // 3. 执行工具调用
    for i, toolCall := range assistantMsg.ToolCalls() {
        toolResult, _ := tool.Run(ctx, ToolCall{...})
        // 权限拒绝 → 中断所有后续调用
        if errors.Is(toolErr, permission.ErrorPermissionDenied) {
            break
        }
    }
    
    // 4. 如果有工具调用 → 把结果追加到消息历史 → 继续循环
    if finishReason == FinishReasonToolUse {
        msgHistory = append(msgHistory, assistantMsg, toolResults)
        continue  // 回到第1步
    }
    
    // 5. 没有工具调用 → 循环结束
    return AgentEvent{Done: true}
}
```

### 权限模型

```go
// 每次工具调用都向用户请求权限
func (s *permissionService) Request(opts CreatePermissionRequest) bool {
    // 1. 检查是否是自动批准的session
    if slices.Contains(s.autoApproveSessions, opts.SessionID) {
        return true
    }
    // 2. 检查是否已在session内授权过
    for _, p := range s.sessionPermissions {
        if match(p, permission) { return true }
    }
    // 3. 弹出权限请求，等待用户批准/拒绝
    respCh := make(chan bool, 1)
    s.pendingRequests.Store(permission.ID, respCh)
    result := <-respCh  // 阻塞等待用户
    return result
}
```

### 核心洞察

| 特征 | 做了什么 | 没做什么 |
|:----:|:---------|:---------|
| **循环** | LLM→工具→结果→循环 | 没有plan→observe→reflect |
| **权限** | 每次工具调用都要用户确认 | 没有自主权限判断 |
| **会话** | SQLite持久化+父子session | 没有跨session记忆 |
| **自修改** | 能读写任何文件 | 不能改自己的源码 |
| **自进化** | 完全不自进化 | — |

## 二、Claude Code（Anthropic · 闭源）

### 架构（从AGENTS.md逆向）

```
Claude Code (Node.js · 闭源)
├── agent/                ← Agent循环
├── tools/                ← 工具集（read/write/bash/edit/glob/grep/lsp）
├── permission/           ← 权限系统（分层）
├── session/              ← 会话管理
├── context/              ← 上下文管理
├── memory/               ← 记忆系统
├── provider/             ← 模型调用（Claude）
└── tui/                  ← 终端UI
```

### 从AGENTS.md逆向的关键设计

```yaml
# Claude Code的核心约束（来自AGENTS.md）

# 1. Prompt缓存是神圣的
"Per-conversation prompt caching is sacred.
 Anything that mutates past context invalidates that cache."

# 2. 核心是窄腰，能力在边缘
"The core is a narrow waist; capability lives at the edges."

# 3. 不要推测性基础设施
"Speculative infrastructure — hooks with no concrete consumer"

# 4. 不要新的核心工具（除非终端+文件不够）
"A new core tool when terminal + file already do the job"

# 5. 行为契约优于快照
"Behavior contracts over snapshots"
```

### 与OpenCode的区别

| 维度 | OpenCode | Claude Code |
|:----:|:---------|:------------|
| **权限模型** | 每次都问用户 | 分层权限+session级自动批准 |
| **上下文管理** | 简单截断 | 智能压缩（ContextCompressor） |
| **记忆** | 无 | 有（跨session） |
| **LSP集成** | 有 | 有 |
| **自修改** | 能改文件 | 能改文件 |
| **自进化** | 无 | 无 |

### 核心洞察

CC的关键设计决策：

1. **Prompt缓存神圣不可侵犯**——这意味着不能随意修改system prompt。openLLM的自递归改进如果改了prompt，会打破缓存，成本翻倍。

2. **核心窄腰**——CC故意不在核心加功能，而是让能力在边缘（skill/plugin/MCP）增长。openLLM可以借鉴：核心引擎要小，四体是核心的一部分还是边缘插件？

3. **行为契约优于快照**——测试应该验证行为关系，不是冻结当前值。这对openLLM的自进化很重要：改了代码后，测试必须验证"行为是否正确"，不是"输出是否和之前一样"。

## 三、OpenClaw（TypeScript/Node.js · 开源）

### 架构

```
OpenClaw (Node.js · "龙虾")
├── gateway/              ← 自托管网关
├── channels/             ← 多频道（飞书/钉钉/企业微信/Discord/iMessage）
├── agents/               ← Agent管理
├── llm/                  ← 模型适配
├── tools/                ← 工具系统
├── memory/               ← 记忆系统
└── config/               ← 配置管理
```

### 核心定位

OpenClaw不是"Agent"——是**Agent网关**：

```
用户在飞书说话
    ↓
OpenClaw网关
    ├── 接收飞书消息
    ├── 路由到Agent
    ├── Agent处理
    ├── 结果返回网关
    └── 网关发回飞书
```

### 与Hermes的对比

| 维度 | OpenClaw | Hermes |
|:----:|:---------|:-------|
| **定位** | Agent网关 | Agent平台 |
| **频道** | 飞书/钉钉/企业微信/Discord/iMessage | Telegram/飞书/微信/元宝/Discord |
| **Agent** | 内置简单Agent | 完整Agent（tools/skills/cron/memory） |
| **Skill系统** | 插件机制 | 完整skill生命周期 |
| **部署** | Docker/Node.js | Python/Docker |

### 核心洞察

OpenClaw的价值不在Agent本身——在**网关模式**。它证明了一件事：

**"Agent不需要绑定在一个界面里。它可以同时存在于多个聊天应用中。"**

openLLM可以借鉴：四体（ISA/IO-S/ISN/IKO）不应该绑定在一个运行时里——它们应该可以跨平台存在。

## 四、OpenHuman（Rust + Tauri · 开源）

### 架构

```
OpenHuman (Rust + Tauri · 桌面应用)
├── core/                 ← Agent核心
├── memory/               ← Memory Tree（记忆树）
├── context/              ← TokenJuice（智能压缩）
├── integrations/         ← 118+集成
├── gui/                  ← 桌面UI（Tauri）
└── providers/            ← 模型适配
```

### 核心创新

#### 1. Memory Tree（记忆树）

```
用户记忆
├── 项目记忆
│   ├── 项目A
│   │   ├── 决策历史
│   │   ├── 代码变更
│   │   └── 人物关系
│   └── 项目B
├── 人物记忆
│   ├── 张三（同事）
│   └── 李四（朋友）
└── 知识记忆
    ├── 技术偏好
    └── 工作习惯
```

OpenHuman把用户的所有信息组织成**树状结构**——不是扁平列表，是层级化的知识图谱。

#### 2. TokenJuice（智能压缩）

OpenHuman有一个叫TokenJuice的系统——智能地压缩上下文，只保留最重要的信息。这和Hermes的ContextCompressor是同一个思路。

#### 3. 主动感知

```
传统Agent：用户问 → Agent答
OpenHuman：用户在做什么 → Agent主动理解 → Agent主动帮忙
```

OpenHuman能**主动感知用户的工作上下文**——不需要用户明确请求。

### 核心洞察

| 特征 | OpenHuman | openLLM可以学什么 |
|:----:|:---------|:----------------|
| **记忆树** | 层级化记忆结构 | Δ胶囊也可以组织成树状 |
| **TokenJuice** | 智能上下文压缩 | self_compact.py的进阶版 |
| **主动感知** | 不等用户问就主动工作 | IO-S的prospective_memory进阶 |
| **118+集成** | 连接各种外部工具 | ISN的skill系统进阶 |
| **Rust性能** | 桌面级响应速度 | 性能优化参考 |

## 五、四个项目对比

### 谁做了什么

| 维度 | OpenCode | Claude Code | OpenClaw | OpenHuman |
|:----:|:---------|:------------|:---------|:----------|
| **语言** | Go | Node.js | TypeScript | Rust+Tauri |
| **Agent循环** | ✅ | ✅ | ✅ | ✅ |
| **工具系统** | ✅ | ✅ | ✅ | ✅ |
| **权限模型** | ✅ 简单 | ✅ 分层 | ⚠️ 基础 | ⚠️ 基础 |
| **记忆** | ❌ | ✅ | ✅ | ✅✅ |
| **跨平台** | ❌ CLI | ❌ CLI | ✅✅ | ✅ 桌面 |
| **自修改** | ⚠️ 改文件 | ⚠️ 改文件 | ❌ | ❌ |
| **自进化** | ❌ | ❌ | ❌ | ❌ |
| **自我递归改进** | ❌ | ❌ | ❌ | ❌ |

### 关键发现

**四个项目都没有"自我递归改进"能力。**

它们都能改文件（OpenCode/CC），但都不能改自己的源码。它们都是"人指挥Agent改代码"——不是"Agent自己决定改什么"。

**openLLM要做的，是这四个项目的交集 + 自递归改进。**

## 六、openLLM该学什么

### 从OpenCode学

1. **Agent循环**：LLM→工具→结果→循环。简单直接。
2. **事件总线**：pubsub模式，解耦Agent和UI。
3. **父子Session**：task可以spawn子session。

### 从Claude Code学

1. **Prompt缓存神圣**：改prompt有成本，要慎重。
2. **核心窄腰**：核心要小，能力在边缘。
3. **行为契约**：测试验证行为关系，不冻结输出。

### 从OpenClaw学

1. **网关模式**：Agent不绑定界面，可以跨平台。
2. **频道隔离**：不同聊天应用的消息互不干扰。

### 从OpenHuman学

1. **记忆树**：层级化记忆比扁平列表好。
2. **主动感知**：不等用户问就主动工作。
3. **TokenJuice**：智能压缩比简单截断好。

---

## 七、openLLM的独特之处

四个项目都没有的，openLLM要做的：

| 独特性 | 四个项目 | openLLM |
|:------:|:---------|:--------|
| **自我递归改进** | 都没有 | ✅ LLM可以改openLLM源码 |
| **四体安全框架** | 都没有 | ✅ IKO审计+IO-S规划+ISA记忆+ISN工具 |
| **守恒律度量** | 都没有 | ✅ d×r×log(L)≈K_W实时监控 |
| **递归自进化** | 都没有 | ✅ 改完→测试→审计→记忆→再改 |

**openLLM不是第5个Agent框架——是唯一一个能让LLM改自己源码的Agent平台。**

## 八、架构蓝图

综合四个参考项目，openLLM的架构应该是：

```
openLLM（自递归改进平台）
│
├── 🔄 Agent循环（学OpenCode/CC：LLM→工具→结果→循环）
│   └── plan→act→observe→reflect（加了反思阶段）
│
├── 🧠 记忆树（学OpenHuman：层级化记忆）
│   ├── Δ胶囊（语义记忆）
│   ├── TextCapsule（可读记忆）
│   └── Memory Tree（结构化记忆）
│
├── 🛡️ 四体安全框架（openLLM独有）
│   ├── IKO：修改必须审计
│   ├── IO-S：修改必须规划
│   ├── ISA：修改必须记忆
│   └── ISN：修改必须用标准skill
│
├── 📡 跨平台网关（学OpenClaw：不绑定界面）
│   ├── 频道适配器
│   └── 消息路由
│
├── 🔧 工具系统（学CC：核心窄腰，能力在边缘）
│   ├── 核心工具（read/write/bash/search）
│   └── 扩展工具（skill/MCP/plugin）
│
└── 💾 自递归改进管线（openLLM独有）
    ├── LLM读源码
    ├── LLM产生修改
    ├── IO-S规划验证
    ├── IKO审计
    ├── 测试通过
    ├── git commit
    ├── 守恒律检查
    └── 生效 or 回滚
```
