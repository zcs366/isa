# 17层工作详解

## 绪论

今天（2026-06-28）做的事：把18篇论文的17层设计要求，从"纸上的想法"变成了"可运行的代码"。

结果：IO-S从790行/6个syscall → 3500行/24个syscall。

---

## 一、17层是什么

17层不是预先设计的——是6天（06-22→06-27）每天读论文，从论文的实验和结论中**自然浮现**的17个设计要求。每个要求回答一个核心问题：

**"Agent框架要长期运行，必须解决什么问题？"**

六个板块，17个问题：

| 板块 | 层数 | 问题 |
|:----:|:----:|------|
| 正确性 | 6层 | "做对了没有？" |
| 可持续性 | 3层 | "能跑多久？" |
| 自进化 | 2层 | "能变多好吗？" |
| 协作 | 2层 | "能和别人配合吗？" |
| 解释 | 1层 | "为什么这样做？" |
| 规划+恢复+经济 | 3层 | "未来怎么走？崩了怎么办？谁付钱？" |

## 二、17层逐层详解

### 第一板块：正确性 (L1-L6)

> **核心问题**："Agent做对了没有？"

#### L1 · 输入侧防护
- **论文**：Layered-Security RAG + MACR
- **问题**：检索到的内容可能覆盖Agent的指令（prompt injection via RAG）
- **今天的做法**：构建 `pipeline.py`（ISA三层防御）。处理层→认知层→执行层，每一层有自己的守门人。攻击必须连续突破三层才能成功。
- **IO-S模块**：`syscall/pipeline.py` · 120行
- **测试**：5/5通过

#### L2 · 决策侧治理
- **论文**：同上
- **问题**：多个信息源可能给出冲突的决策，Agent不能被任何一个源独裁
- **今天的做法**：pipeline.py内建冲突消解机制。多源信号到达时，先投票后加权，不是先到先得。
- **IO-S模块**：同上（pipeline.py内含）

#### L3 · 工具侧开放
- **论文**：AutoPass
- **问题**：Agent做决策不能只靠自己的"直觉"（LLM训练时的记忆），必须让外部证据说话
- **IO-S模块**：`syscall/evidence.py` · 140行。Agent的每次判断必须附带可验证的证据链。无证据的判断会被审计拦截。
- **测试**：20/20通过

#### L4 · 动作侧隔离
- **论文**：SEB (Systemic Evolutionary Benchmark)
- **问题**：工具执行的权威不应该驻留在LLM内部——LLM说"删文件"和"真的删文件"是两回事
- **今天的做法**：IO-S的cap_policy确保LLM只能"建议"，执行层有独立的权限检查。LLM的决策和文件系统的操作在两个不同的进程里。
- **IO-S模块**：`syscall/cap_policy`（原有模块，本次未改动）

#### L5 · 评估侧稳健
- **论文**：Contagion (Memory Contagion)
- **问题**：一个模块的偏差会像病毒一样传染整个系统
- **IO-S模块**：`syscall/gamma_monitor.py` · 140行。全系统级别的偏差传染监控。每次模块间的交互都记录到Γ矩阵，定期检查是否有异常传播。
- **测试**：3/3通过

#### L6 · 内容侧净化
- **论文**：RoleConfusion (ICML 2026)
- **问题**：Agent的CoT里可能藏着情绪、语气、修辞——这些会潜意识地steering后续决策
- **IO-S模块**：`syscall/sanitizer.py` · 140行。每次Agent输出进入决策前，先剥离情绪和修辞，只保留事实和逻辑。
- **测试**：11/11通过

---

### 第二板块：可持续性 (L7-L9)

> **核心问题**："能跑多久？"

#### L7 · 性能
- **论文**：Kamera (KV Cache复用)
- **问题**：token和时间不能无限膨胀。长时间对话的KV cache必须可以复用，不能每次都重算
- **IO-S模块**：`syscall/cache_strategy.py` · 150行。高频访问的KV cache常驻，最近使用的不清理，长时间不访问的才压缩。
- **测试**：7/7通过

#### L8 · 持久运行
- **论文**：Self-Compacting (自压缩)
- **问题**：长周期运行不能退化。Agent的上下文越用越长，必须自己能压缩自己
- **IO-S模块**：`syscall/self_compact.py` · 120行。3模板9规则。语境稠密时压缩，稀疏时保留。不是删——是蒸馏。
- **测试**：8/8通过

#### L9 · 前瞻
- **论文**：TriggerBench
- **问题**：资源消耗必须可预测。不能到某个点突然"认知悬崖"——上下文到100K时突然崩溃
- **IO-S模块**：`syscall/prospective_memory.py` · 120行。前瞻记忆模块在资源接近阈值时自动降级，不等到崩溃。
- **测试**：5/5通过

---

### 第三板块：自进化 (L10-L10.b)

> **核心问题**："Agent能变多好吗？改了之后还对吗？"

#### L10 · 自进化机制
- **论文**：Self-Harness + APEX + HarnessSensitivity
- **问题**：Agent能不能自己改进自己的prompt、策略、工作流？而且改了之后不能变差
- **IO-S模块**：`syscall/self_evolve.py` · 210行。三阶段闭环：评估（当前表现）→ 变异（生成候选改进）→ 挑选（用对照实验选最好的）。不是LLM自己改自己——是LLM生成候选，实验验证，数据挑选。
- **测试**：12/12通过

#### L10.b · 自进化边界
- **论文**：同上（HarnessSensitivity边界条件）
- **问题**：改进了但变质了——怎么防止？
- **今天的做法**：self_evolve.py内建了"质量红线"。变异后的候选必须通过baseline对比测试，偏差超过阈值的自动回滚。
- **IO-S模块**：同上（内含在self_evolve.py的挑选逻辑里）

---

### 第四板块：协作 (L11-L11.b)

> **核心问题**："能和别人配合吗？配合的成本能度量吗？"

#### L11 · 协作协议
- **论文**：SSVP (Secure Shared Vision Protocol)
- **问题**：多个Agent协作时，一个Agent不能发布一个让所有人都执行的命令——必须有门控
- **IO-S模块**：`syscall/gate_sync.py` · 170行。CDS协议：每条跨Agent指令必须经过"发布→确认→执行"三步。没有全域广播——只有点对点确认。
- **测试**：6/6通过

#### L11.b · 协作优化
- **论文**：MAS-PromptBench
- **问题**：超过4个子Agent就会内耗——协作开销大于收益时，必须自动拆组
- **IO-S模块**：`syscall/team_scale.py` · 60行。动态评估子Agent数量与任务复杂度的比值。>4时自动拆组建议。
- **测试**：4/4通过

---

### 第五板块：解释 (L12)

> **核心问题**："为什么这样做？行为的codelength reduction可测量吗？"

#### L12 · 可解释性
- **论文**：AgenticCompressor (智能体压缩器)
- **问题**：Agent的每个决策不是等价的——有些决策节省了大量token，有些是无效的。必须能量化。
- **IO-S模块**：`syscall/bits_metric.py` · 170行。每个验证器的边际价值按比特度量。"这个决策压缩了多少信息"是可以计算的。
- **测试**：5/5通过

---

### 第六板块：规划+恢复+经济 (L13-L15)

> **核心问题**："未来怎么走？崩了怎么办？谁付钱？"

#### L13 · 规划
- **论文**：PEEU (Planning with Expert Experience and Uncertainty)
- **问题**：Agent只能做当前的tool-call，没有长期规划能力。不能"先做A再做B再做C"——每次都是从零开始
- **IO-S模块**：
  - `syscall/planner.py` · 97行。任务分解(decompose) + 经验回溯(hindsight)
  - `syscall/async_planner_executor.py` · 165行。异步调度器，2 worker并行
  - `syscall/hindsight_loop.py` · 97行。从失败中提取高层经验
  - Process状态机 +PLANNING状态（+57行）
- **测试**：35/35通过

#### L14 · 恢复
- **论文**：Concordia
- **问题**：Agent崩溃后怎么恢复？不能丢掉进行中的任务
- **IO-S模块**：`syscall/checkpoint.py` · 210行。定期快照当前状态到GPU内存。崩溃时从最近的检查点恢复，不丢进行中的任务。
- **测试**：20/20通过

#### L15 · 经济
- **论文**：Web4 Agent Economy
- **问题**：多个Agent协作时，资源和成果如何计量和分配？
- **IO-S模块**：`syscall/economy.py` · 120行。Agent间的资源计量和分配。MCP Tunnel兼容层。
- **测试**：5/5通过

## 三、守恒律作为"骨架"

17层不是17个独立的积木——它们是**信息守恒** `d×r×log(L)≈K_W` 的17个工程投影：

```
d（有效维度）    → L1-L6 正确性层。错误导致维度膨胀，守恒律约束它。
r（递归轮次）   → L7-L9 可持续 + L13 规划。循环不能失控，规划约束r的上限。
log(L)（上下文） → L10-L11.b 自进化+协作。让有限上下文承载更多Agent能力。
K_W（容量常数）  → L12+L15 解释+经济。可度量的上限。
```

`conservation_law.py`（280行）不是边角模块——是所有24个syscall运行时的度量骨架。每个模块的d/r/L都在被实时测量。

## 五、与Hermes的关系

### 比喻

```
Hermes = 物理国土（马路、水电、通信网）
IO-S   = 交通规则 + 红绿灯 + 交警 + 驾驶证考试
ISA    = 驾驶员（记忆路线、记住上次哪里堵）
ISN    = 修车厂（技能库，需要什么工具去哪里找）
IKO    = 交警（检查输出格式、审计违规）
```

### 具体关系

| 维度 | Hermes | IO-S |
|:----:|:------|:----|
| **提供什么** | 工具调用（tools）、技能管理（skills）、cron调度、多频道分发、plugin框架 | 进程管理（process）、任务规划（planner）、审计（audit）、度量（conservation） |
| **不做** | 不管Agent怎么思考、怎么决策、怎么自进化——只提供基础设施 | 不管工具怎么调、技能怎么写、消息怎么发——只管决策和治理 |
| **接口** | Agent调Hermes tool → 工具返回 | Agent调IO-S syscall → 决策返回 |
| **启动关系** | Hermes必须先启动 | IO-S在Hermes之上启动 |

### 能从Hermes独立出去吗？

**技术上可以，但价值会降低。**

1. **代码独立**：IO-S的24个syscall模块全部是纯Python（零外部依赖）。它们不import Hermes的任何代码。`from syscall.planner import ...` 能在任何Python环境中跑。

2. **功能独立**：IO-S能自己跑测试、自己做规划审计——不需要Hermes的tools/skills。

3. **但价值在集成**：
   - IO-S的planner需要知道"有什么工具可用"→ 需要 `skill_discovery.py`（今天建的桥）→ 这桥的一端是IO-S，另一端是Hermes的skill目录
   - IO-S的checkpoint需要"在哪个进程保存"→ 进程是Hermes管理的
   - IO-S的gamma_monitor需要"跨进程偏差"→ 进程间通信是Hermes的频道

**结论**：IO-S可以独立编译、独立测试。但在实际运行中，它和Hermes是共生关系——IO-S是决策层，Hermes是执行层。拆开双方都能活，但都不完整。

## 六、与openLLM的关系

### 比喻

```
openLLM = 国家
ISA     = 记忆部（负责"记得"）
IO-S    = 治理部（负责"决策"）
ISN     = 技能部（负责"会做"）
IKO     = 审计部（负责"输出合规"）
```

### 具体关系

| 维度 | openLLM | IO-S |
|:----:|:-------|:----|
| **是什么** | 四体（ISA/IO-S/ISN/IKO）的统一体，是产品/愿景 | 四体中的一个子系统，是工程实现 |
| **谁做决策** | 四体协调层IDC | IO-S内的planner/audit |
| **谁执行** | ISN的skill执行 | IO-S的syscall执行 |
| **谁审计** | IKO的validate_tentacle | IO-S的包拯audit |

### IO-S在openLLM中的位置

```
openLLM = ISA + ISN + IKO + IO-S
              ↑     ↑     ↑     ↑
            记忆   技能  审计  决策
              ↑     ↑     ↑     ↑
            波扩散  SKILL  validate  24个syscall
            Δ胶囊  case_lib  七通道  Process状态机
              ↑     ↑     ↑     ↑
              └─────┴─────┴─────┘
                   Hermes（平台）
```

## 八、总结

```
18篇论文 → 17层设计要求 → PAL(P0/P1/P2) → 24个syscall → 3500行代码
    ↑                           ↑                    ↑              ↑
  6天日报                       五人合议              七神划界       包拯审计
  36份文档                     35项任务             7道界碑        零错误
```

**一句话**：今天把18篇论文里的17个想法，从纸上搬到了电脑里。搬的过程中，IO-S从一个6人小队变成了24人军团。它现在能自己规划、自己恢复、自己审计、自己度量。

**与Hermes**：IO-S是Hermes上面的决策层。能独立测试，不能独立运行。
**与openLLM**：IO-S是openLLM四体中的一个体。四体合起来才是openLLM。
**与ISN/IKO**：IO-S↔ISN今天建了桥（skill_discovery），IO-S↔IKO是审计通道。
**独立性**：代码100%独立。运行时50%依赖Hermes（进程管理+工具调用）。完整运行100%依赖四体协同。
